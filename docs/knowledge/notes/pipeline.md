## Superseded
- **`RECOV-10`'s "rethrow the contained throwable UNCHANGED" is broken by the obvious Ruby spelling: a bare `raise error` silently assigns whatever exception is in flight as that error's `#cause`, and the in-flight exception can be the *caller's*.** Supersedes `pipeline/b3f74458` ("Dispatch unwraps a Failure by re-raising the contained error unchanged, with no wrapping or substitution"), whose rule is exactly right and whose Ruby realisation is a trap the entry cannot warn about because it names no code. Verified on 2026-09-08 against 3.2.11, 3.4.10 and 4.0.6. **The facts, uniform across the range.** `raise stored` when `$!` is non-`nil` and `stored.cause` is `nil` sets `stored.cause` to `$!` — Ruby's implicit cause assignment — so the object the caller receives is **not** the object the `Failure` carried: it has acquired a parent it never had. `$!` is dynamically scoped to the thread and is therefore non-`nil` inside a method **called from** a caller's `rescue` block, which is ordinary consumer code (`begin; …; rescue; client.send(request); end`) and needs no `rescue` anywhere in core to reach; measured, the surfaced error came back carrying "the CALLER's unrelated in-flight error" as its cause. `raise stored, cause: nil` suppresses the assignment; it does **not** clear a cause the error legitimately already has (measured: a pre-existing cause survives, same object); and it never trips `ArgumentError: circular causes`, including against the caller-defined `#cause` overrides `../notes/error-handling.md` records as the only route to a cycle. `raise stored, cause: stored.cause` behaves identically in every case measured but calls a caller-overridable method to do it. **What the SDK does**, per `docs/work/mvp/phase4/phase4b/2026-09-08-phase4b-recovery-primitives-design.md`: every `RECOV-10` unwrap and every place core re-raises an error it is carrying rather than one it just rescued is written `raise error, cause: nil`, with the reason at the call site. Outside the recovery chain there is exactly one such place and it is phase 2's: `Dexpace::Hooks.notify` collects the first handler failure, runs the rest of the list, and re-raises the stored object afterwards, and `$!` at that line is measurably the *caller's* in-flight exception whenever a hook list is drained from inside a `rescue`; phase 4b's `DEF-32` change rewrites it as `raise failure, cause: nil` in the same edit that adds the suppressed trail. **How far `cause: nil` reaches is worth stating exactly, because it is less than the rule sounds.** It suppresses an assignment the re-raise would itself make; it cannot undo one already made. Measured on all three: an error the caller's code *raised* while an outer `rescue` was in flight acquired that exception as its cause at its own `raise`, and `cause: nil` at a later re-raise leaves it in place — so the spelling changes the surfaced object only for an error that reaches the re-raise with `cause == nil`, which is exactly `RECOV-10`'s own named case, "a recovery step **constructing** the error and returning a Failure". The consequence for tests is concrete: a `RECOV-10` fixture whose `Failure` carries a *raised* error makes `assert_nil error.cause` fail against a correct implementation, so the fixture must construct the error and never raise it. The `RECOV-10` test asserts `#cause` is unchanged across the unwrap while an unrelated exception is in flight — an assertion a test written without this fact would not think to make, and which the bare spelling passes whenever the suite happens not to be inside a `rescue`. `pipeline/c76ca402` (the `RECOV-10`/`RECOV-11` spec rule) and `pipeline/77de2b12` are unaffected and adopted verbatim.
