## Reference
- **`XCUT-11`'s audit predicate, and why *frozen with no instance variables* is the wrong one.** **The harvested rule cross-cutting-invariants/89eb6533 stands unchanged and is NOT overridden** — its key is deliberately left unbackticked here, because backticking it is what makes every query result print `[overridden by notes/…]` beside it, and a correct rule should not read as overridden. What this note adds is the *audit consequence* the rule implies and does not state. That rule fixes the latch shape this port uses — "close idempotence is implemented as a latch, a `@closed` boolean flipped under a `Thread::Mutex`, held only across the flip and released before `#release` runs … because Ruby's Mutex is per-fiber-owned and non-reentrant" — and extends it with the consequence that rule has for the *audit* rather than for the implementation. `XCUT-11` requires that "per-call mutable state MUST live on the call's stack/local state, not the shared instance, and any shared mutable state MUST be synchronized", and nine hand-forward rows across five phase documents name nine different objects as "the audited shared instance" without any phase defining what audited means. The obvious predicate — frozen, and `instance_variables` empty — condemns every `Dexpace::Closeable` in the SDK, because the latch this very rule prescribes *is* mutable state on a shared instance. So phase 9 fixes the predicate as: **frozen with no instance variables, or every instance variable declared by the subject as one of two named kinds — a `Thread::Mutex` together with the state that mutex guards, or `Closeable`'s `@closed` latch** — with the declaration supplied per object, because only the object knows which ivar is its mutex and which is the state under it. The behavioural half is two shapes rather than one: the sixteen-thread race `XCUT-11`'s own conformance clause names, and the **two-fibers-on-one-thread** shape phase 8b handed forward as "the only shape that proves a per-fiber mutex is not held across a suspension point", which a thread-only test cannot see for the reason this harvested entry gives. Verified on 3.2.11, 3.4.10 and 4.0.6: `instance_variables` on a frozen instance holding one mutex returns `[:@lock]` identically, and a `Data.define` subclass is frozen on construction on all three. `Dexpace::Conformance::SharedInstance.audit(object, mutable:, ids:)` is the predicate.

- **The repository-wide invariant scans are Rake gates over `RubyVM::AbstractSyntaxTree`, not conformance assertions, and a `:CALL`-only scan is wrong.** Relates to cross-cutting-invariants/7e6a9aea (`XCUT-14`'s hard cap and drain-to-cap loop) and, by the same argument, to `XCUT-9`'s single-walk rule and `SEAM-2`'s no-concrete-seam rule — **neither key is backticked, because neither harvested rule is false**; what is added is how each is checked. Four checks handed forward to phase 9 are statements about the **absence of a second implementation** rather than about what one implementation does — `XCUT-9`'s "nothing else walks `#cause`", `XCUT-14`'s "one bounded-map implementation", `SEAM-2`'s negative test over core's tree, and `SSE-37`'s `gates:serde_boundary` `PENDING` list — and none can be a portable conformance assertion, because a scan of `gems/*/lib/` is meaningless in a consumer's process where `gems/` does not exist. They land as Rake gates. The mechanism is `RubyVM::AbstractSyntaxTree` rather than a regex, because `grep '\.cause'` matches a comment, a string, an `# XCUT-9` citation in a test header and the requirement ID itself. Verified on 2026-09-12 on 3.2.11, 3.4.10 and 4.0.6: the module is present on all three and `parse_file` returns a `SCOPE` node on all three. **The PARSER emits no warning of its own under `-w`; a SCANNED FILE's own `-w` diagnostics are a different thing and do reach `Warning.warn`** — which is load-bearing, because phase 0's shared test case overrides `Warning.warn` to raise, so a scanner that parses a file carrying one fails the suite that runs it. An earlier form of this entry said parsing emits no warning full stop, generalising from a measurement taken against a file that carries none; that generalisation is struck. Measured 2026-09-13 on 3.2.11, 3.3.12, 3.4.10 and 4.0.6 against 8a's filed `adapter.rb`, whose `rescue ::StandardError => e` inside `Adapter#dispatch` never reads `e` (8a plan:4858): parsing it emits `assigned but unused variable - e` on all four, and with the gate suite's own `dexpace_test_case` loaded a bare `parse_file` raises `RuntimeError: warning treated as an error (NFR-6)` out of `AstScan.receiver_calls` on all four. **Which suppression works was measured, not assumed:** `Warning[:deprecated] = false` does not reach it, because the warning carries no category; `$VERBOSE = false` silences the `-w` class but leaves the always-on parse warnings firing, and `key :a is duplicated` still raised on all four; only `$VERBOSE = nil` silences both. So `AstScan.parse` is the sole parse entry point in the scanner, opening a `$VERBOSE = nil` window restored in `ensure` so the gate stays armed everywhere else (phase 9 plan:4270-4291, its fixture at plan:138-154 and the test that would error without it at plan:4219-4227, and design Fact 1b). `prism` is absent on the 3.2 floor (`LoadError`) and present at 1.9.0 on 3.4.10 and 1.8.1 on 4.0.6, so the AST route needs no conditional require where Prism would. **Four measured corrections to the obvious implementation, each one a gate that reported clean over a live defect.** (1) A send is **three** node types, not one — `a.cause` is `:CALL`, `b&.cause` is `:QCALL`, a bare `cause` is `:VCALL`, identically on all three — and a `:CALL`-only scanner returned two hits for a fixture containing three `#cause` sends. (2) A **reflective** send bypasses call-syntax scanning entirely: `send(:cause)`, `__send__`, `public_send` and `method(:cause)` took the catch rate from 3 of 7 realistic shapes to 6 of 7, the seventh — `send(variable)` — being statically undecidable. (3) **A Symbol literal is a `:LIT` node on Ruby 3.2.11 and a `:SYM` node on 3.4.10 and 4.0.6**, which is the reverse of the usual direction and is why the reflective scan must name both: naming one gave 6 of 7 on the floor and 2 of 7 on the newer rows, a gate strictest exactly where it runs least — which is why this entry names both node types rather than the one the newest interpreter shows. (4) `Hash` is `:CONST` and `::Hash` is `:COLON3`, so `@h = ::Hash.new` escaped a check naming only the first. **And one clause gains a second line rather than moving — which corrects this entry's own earlier form.** `XCUT-14`'s drain-to-cap clause **is** decidable behaviourally, and phase 9 decides it there: `InvariantSuite#bounded_map_drains` reaches the map's backing store through the driver's `bounded_map_store:` hook, pre-fills it to cap + 5 — the state an overshoot would leave, arranged without a thread — and then performs **one** `set`; 4a's filed drain loop ends at the cap, **8**, and a check-then-evict ends at **13**, identically on 3.2.11, 3.3.12, 3.4.10 and 4.0.6 (phase 9 plan:1670-1689, its failing test at plan:1576-1581 asserting `%i[passed failed]`, and phase 9 design:572 and design:755). **What makes that deterministic is that the observation is an eviction count, not an interleaving** — one insert into an over-cap store either drains back to the cap or evicts exactly once — and the over-cap state is *injected* rather than raced for. The earlier racing attempt is kept here because it is a real finding about **that method** and not about the clause: a check-then-evict map was indistinguishable from a drain loop in 0 of 30 runs on 3.4.10 and 4.0.6 at 16 threads and 0 of 20 at 64 threads by 5000 inserts — because no overshoot ever appeared to observe, which is the structural point `../notes/execution-context.md` already records, that an insert and its drain inside one `synchronize` make an overshoot unreachable rather than merely rare. So racing measures nothing about this clause; **it does not make the clause undecidable, and an earlier form of this entry drew that conclusion and moved the clause to a shape check alone — that inference is struck.** `gates:drain_loop` stays as the **second line**, not the only one: a shape check over `BoundedMap`'s own file asserting the eviction send sits inside a `while`/`until`, with its own stated gap — it proves an eviction send is looped in that file, not that the loop is the only eviction path (phase 9 plan:4564-4574) — and a measured reach of 1 of 3 non-conforming shapes with one false positive and 3 of 4 conforming shapes clean, every miss carried into phase 9 plan, Task 13's gate-miss dispositions (phase 9 design:233). A gate that reports clean while the invariant is broken is worse than no gate, which is why phase 0's failing-fixture discipline applies to these five as much as to its own seventeen.
