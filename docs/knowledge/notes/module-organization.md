## Conflicts
- **Autoloading: the design wins — `lib/dexpace.rb` issues explicit `require`s and no gem in this repository loads Zeitwerk.** Resolves `module-organization/bf6411ad`. This is a library-versus-application distinction rather than a preference: Zeitwerk is itself a gem, so `require "zeitwerk"` in `dexpace-core` is an `add_dependency` line, and `dexpace-core.gemspec` is asserted to have zero runtime dependencies (`SEAM-1`, `NFR-1`). An application can afford the autoloader; a zero-dependency core cannot. What the SDK does instead: `lib/dexpace.rb` requires the whole tree explicitly, which also turns the require-graph audit into a text scan rather than a runtime trace; adapter gems follow the same rule for consistency even though `NFR-2`'s one-third-party-library budget would technically permit them an autoloader. Everything else the styleguide chapter asks for is kept unchanged — the file-path-to-constant mapping, one constant per file, nested `module`/`class` form, no load-time side effects, no top-level constants outside `Dexpace::` — so the convention Zeitwerk would have enforced is enforced by review and by the runtime surface snapshot instead. The styleguide-amendment alternative (carving out gems whose dependency budget forbids an autoloader) was considered and not taken; this is recorded as an SDK deviation instead.

- **File paths under `lib/dexpace/http/` and `lib/dexpace/error/` organise files; they are not namespace segments, and the public wire model's constants are flat.** Resolves `module-organization/3ff5433e`. Two binding documents disagree and the rule has to break one of them: `docs/sdk-design-ruby/02-gem-and-workspace-layout.md` §2.3 puts the domain model under `lib/dexpace/{http,...,error}/**.rb`, while §3.2, §3.7 and §5 of the same design name the constants `Dexpace::Response`, `Dexpace::RequestOptions`, `Dexpace::TransportError` and `Dexpace::PipelineError` — no `HTTP::` or `Error::` segment — and every later phase is written against those names. The constant wins, and the styleguide's own chapter asks for exactly that: `module-organization/7d1041eb` says to re-export the public contract from the gem's top-level namespace (`Commerce::Order` rather than `Commerce::Checkout::Order`). This port satisfies it by *defining* the constant there rather than by aliasing, because an alias would put two names for one class into both artifacts `NFR-4` diffs — the `sig/**/*.rbs` tree and the runtime surface manifest. What the SDK does instead: `Dexpace::Request` lives in `lib/dexpace/http/request.rb` and `Dexpace::InvalidArgumentError` in `lib/dexpace/error/invalid_argument_error.rb`; a nested public constant still maps exactly (`Dexpace::Headers::Builder` is `lib/dexpace/http/headers/builder.rb`); and a subsystem whose design already names it with a namespace keeps it, so `Dexpace::IO::Buffer`, `Dexpace::Serde::JSON`, `Dexpace::Instrumentation::Bundle` and `Dexpace::Outcome::Success` are unaffected. Everything else chapter 12 asks for is kept: one public constant per file, nested `module`/`class` form, no load-time side effects, nothing defined outside `Dexpace::`. The rule's stated motivation is Zeitwerk, which `../notes/module-organization.md` already records this port as not using — `lib/dexpace.rb` requires every file explicitly, so nothing mechanical depends on the mapping and the convention it protected is protected instead by the runtime surface snapshot. The styleguide-amendment alternative (scoping rule 12.2's filename clause to autoloaded projects) was considered and not taken; this is recorded as an SDK deviation instead (phase 1, P1-1).
