## Conflicts
- **Static typing stack: the design wins — RBS signatures under `sig/`, gated by `rbs validate` and `steep check`, and no Sorbet anywhere in this repository.** Resolves `type-system/93dc79aa`. The decisive fact is mechanical rather than aesthetic, and it is a library-versus-application one: Sorbet's `sig` blocks are executed by `sorbet-runtime`, so `# typed: strict` with runtime-checked signatures forces `add_dependency "sorbet-runtime"` into every gemspec that carries a `sig` — including `dexpace-core`, whose gemspec is asserted to contain zero `add_dependency` lines (`SEAM-1`, `NFR-1`). An application pays that dependency once; a zero-dependency core would be imposing it on every consumer, and `NFR-11`'s "no constant outside `Dexpace::` and a fixed stdlib allowlist in any public signature" would be violated by the `T::` constants themselves. RBS is the opposite shape: signatures are data files, `rbs` and `steep` are development-only, and `sig/` ships inside each gem so a consumer's own `steep check` sees it. What the SDK does instead: every public entity has an RBS signature (`NFR-3`); `rbs validate` plus `steep check` are blocking gates; Steep adoption is target-by-target in the `Steepfile` rather than a blanket ignore, because Steep on metaprogramming-heavy code produces false positives; the `NFR-4` API lock is a diff of `sig/**/*.rbs` against the previous release tag, paired with a runtime surface snapshot because RBS cannot see `Data.define`'s generated readers. What is lost and is not replaced: Sorbet's runtime `sig` enforcement — RBS is static only — so the styleguide's assertion-density rule is met by explicit `raise` preconditions in `.build` and at the wire boundary instead. The `# typed:` sigil is not written in any file here, and the `Sorbet/StrictSigil` cop is not part of this repository's cop set. The styleguide-amendment alternative (carving out zero-runtime-dependency gems to use RBS in place of Sorbet) was considered and not taken; this is recorded as an SDK deviation instead.
