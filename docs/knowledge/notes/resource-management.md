## Conflicts
- **The per-call I/O timeout rules do not reach the byte-streaming layer: `IO-40` forbids it, and the timeouts belong to the transport that owns the socket.** Resolves `resource-management/c86d4e58` ("Set a per-call timeout at the client level for every external I/O call — for example `Net::HTTP#read_timeout`, `redis.timeout`, `pg`'s `:connect_timeout`, or `Async::Task#with_timeout` in an async context"), `resource-management/ed29d0f5` (timeouts at single-network-call granularity rather than one global timeout) and `resource-management/2b9040ef` (every I/O timeout a named constant). Read literally, all three reach `Dexpace::IO::BufferedSource` and `BufferedSink`, which do perform external I/O calls against a caller-supplied stream — and following them there would violate a MUST. **`IO-40`:** "These streaming contracts MUST NOT impose their own read/write timeout or deadline; the adapter wraps foreign streams with a no-op timeout, delegating all deadline enforcement to the transport. A mirroring/wrapping sink MUST NOT swallow OR duplicate the wrapped stream's cancellation/interrupt handling … The prompt-cancellation-of-blocked-I/O guarantee itself belongs to the wrapped transport, not to these contracts (the in-memory buffers never block)." The roadmap's precedence rule settles it — a corpus rule carrying a requirement ID beats a general styleguide default — and the requirement is right on the merits rather than merely normative: a timeout imposed one layer below the transport is a second, uncoordinated deadline over the same socket, which is exactly the "a global timeout does not bound the total blocking time of a batch of sequential calls" failure `ed29d0f5` itself warns about, arriving from the other direction. **Where the three rules *are* paid in this codebase:** phase 8's transports, which own the socket and set `open_timeout`/`read_timeout`/`write_timeout` per call (`docs/sdk-design-ruby/03-seam-by-seam-idiomatic-mapping.md` §3.3, `docs/sdk-design-ruby/08-instrumentation-and-configuration.md` §8.3), with the values coming from phase 5's layered configuration chain as named settings rather than literals — which is `2b9040ef` satisfied by a configuration key instead of a constant. Two rules in the same chapter are **not** resolved here and are adopted unchanged by phase 3a: `resource-management/1676974d` ("never rely on finalizers or the garbage collector for deterministic resource cleanup"), which is the same rule design §7.1 derives independently from the `Enumerator`/`ensure` asymmetry, and `resource-management/bf5560dc` (block form for every closable resource), which phase 3a adopts for the two factories that take ownership of an external stream — `BufferedSource.wrapping(io) { }` and `BufferedSink.wrapping(io) { }` — and not for the factories that own nothing, where there is no resource to leak and `resource-management/43a55896`'s explicit-lifecycle-ownership form is what the no-block variant already is.
